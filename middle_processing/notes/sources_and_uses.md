**三条结论**（13:1315-1324）：
1. **真实挖矿的天花板是 2~5%，瓶颈不在筛选而在「能不能跑起来」** ——
   SWE-rebench 自己点名 install&validate 只有约 14%、只有 31% 的仓库能装成功。

# 二、原始 html 必须做的清洗

## 2.1 为什么原始 html 不能直接用：三组人独立撞的同一个坑

**最硬的一条**：Common Crawl 的原始 WARC **不能用于渲染**，三组人各自独立得出同一结论
（09:250-295，笔记原话「第一个也最容易踩的陷阱」）：

- **UI2Code^N**：只把 CC 的 **URL 当种子重爬**，因为「CC 本身缺图片和 CSS，页面无法被忠实渲染」。
- **WebCode2M**：虽然起点是 CC segment，但管线第一步就是**内联 CSS**，然后必须过 Playwright 渲染。
- **MultiUI / WebUI**：直接自爬，不碰 WARC。

**第二条**：真实页面**大部分不配当监督信号**，这是有人工标注支撑的硬数据（09:250-295）：
WebCode2M 的美学打分器由 **6 名标注员**（CS 本科 + 3 年前端经验）花 **约 2 周**
按 5 条一分制判据打出 **10,000** 个人工分数，**其中 80% 落在 0–1 分**。
ResNet-50 五分类精度 75%、二分类约 90%；上线后 **score<2 剔掉 = 52.5% 的原始数据**。

**第三条**：长度本身让原始页面不可训。Design2Code 平均 **31,216 ± 23,903** token
（min 784 / max 98,637）、158 标签、DOM 深度 13（20:1491）；论文原话
「这远长于现代语言模型的典型最大输出长度」（20:1499），所以它**剔除源码 >100K token 的样本**，
理由是「当前的多模态大模型无法把这么长的内容作为输入处理，也无法解码出这么长的输出」（20:1500-1502）。
对照合成数据 WebSight **647 ± 216** token / 19 标签 / 深度 5（20:1494）——
**真实页面的 token 多 50 倍、标签多 6 倍、DOM 深度 2 倍**（20:1503，WebCode2M §1 原话）。

**第四条**：直接把原始文字塞进 prompt 会让模型崩。
**Sketch2Code：给 InternVL2-8b 全部文字后 HTML 合法率 98.0% → 39.2%、Layout −6.07**；
**Design2Code：Idefics2-8B 的 Text 分 80.3 → 55.6 → 22.6**（Direct → Text-Augmented → Self-Revision）
（20:1244）。笔记结论原话：「**对开源小模型，把文字塞进 prompt 是净负收益**」（20:1247）。

### 闸 6 — 审美过滤

| 做法 | 阈值 | 谁 | 出处 |
|---|---|---|---|
| ResNet-50 五分类打分器，**score<2 删掉** | **删 52.5%**（五分类精度 75% / 二分类约 90%） | WebCode2M | 09:250-295 |
| 人工标注池 | 6 名标注员 × 约 2 周 = **10,000** 个分数，**80% 落在 0–1 分** | WebCode2M | 09:250-295 |
| 测试集构造 | 从约 **2,000** 个 score>4 的样本里 CLIP 去重 + 人工，Short/Mid/Long **各 256** | WebCode2M | 09:250-295 |
| **不要用 CLIP/SigLIP 当美学/质量闸** | CLIP 在同 precision 下 recall 只有 **0.02**；SigLIP 在 10 个 3D 模型上全落 **0.077~0.108** 的窄带 | 本机实测 | 13:1049；13:242-243 |

**这道闸有三条反向证据，必须一起写**（否则会写出错的结论）：
1. **经典计算美学指标全都单向可刷**：留白更多、边缘更少、颜色更少、对齐线更少全都分更高，
   所以 **RL 必然收敛到一张空白单列页**；AIM 的 `cp11` 色彩和谐更糟 ——
   **源码自己注释说模板 X 几乎总是最小距离**，模型会学会去填满色轮（19:1-80）。
2. **Duan et al. CHI 2024 实测：UI 越好，工具表现越差** —— 第一轮 52% 准确率掉到后几轮 **39%**，
   标注一致性 Fleiss κ = **0.112**（19:1-80）。
3. **口味本身不收敛**：DesignPref 让 **20 名专业设计师**判同样的 **600 对**，
   二元一致率只有 **0.624**、**Krippendorff α = 0.248**，**28.5% 的对 pairwise 分歧 ≥96%**；
   在这份数据上用 20× 更大的池训的 UIClip 只到 **57.45%**，个性化到 **60.16%**
   → **任何声称远高于 60% 的全局美学奖励都该先怀疑泄漏**（Webthetics 的 r≈0.85 就被抓到
   train/validation 重叠，真值 LCC≈0.752）（19:1-80）。
→ 所以笔记的结论是：**审美判据只能做双侧区间或否决闸，不能当单调排序器**（19:1-80）。

| MONET（1 亿级生产集） | pHash d=0 + **SSCD ≥ 0.75** | — | 累计 **−7.7%**；**实证 pHash 不可靠：真近重复可达 d=26，而 d=1 已有语义无关的假阳性簇** |
| LAION-400M/5B | **只有 URL ⊕ alt-text 的 bloom filter** | — | **没有图像内容哈希、没有 embedding 去重、没有对评测集去重** |
| GLM-4.1V | CLIP-Score | **≥ 0.3** | — |

- **pHash 的阈值在本库里没有公开推荐值**：09:818-842 明确说「**pHash 没人公布阈值**」；
  13:1033-1034 进一步说 `pHash ≤ 5` / `≤ 8` 这种「业界通常」**查不到任何公开来源，是传说**。
- **阈值必须随库规模重标**：ISC2021 实测**库从 100 万涨到 1,000 万，同阈值下 recall 不变而
  precision 从 0.8 跌到约 0.29**（13:1038-1039）。照抄前必做 MONET 那一步 ——
  **按 0.05 分箱人工抽检**，十万量级只要几十条样本（13:1041-1042）。

**去重会过头（最重要的反向证据，13:1183-1202）**：
FineWeb 实测 **全局去重（96 个 CC 快照互相去）把 15T 压到 4T，最老的快照被删掉 90%，
结果相比不去重几乎没有提升**，远落后 RefinedWeb；而**逐快照独立去重得到 20T token，持平 RefinedWeb**。
作者解释：收益来自打掉「跨全部快照、动辄几十万文档的**巨型重复簇**」，
**对只有几十个副本的小簇继续去重反而有害**。对照实验：2013-48 快照「全局去重后剩的 31B token」
训出来**不如**「被删掉的那 460B 单独去重后的 171B token」。

**去重的收益量级（13:1206-1215）**：
The Stack 代码近重复去重 → permissive 子集 **HumanEval pass@100 27.21% → 37.00%**、
**MBPP 44.99% → 54.69%**；Allamanis「代码重复的恶果」——不去重让指标**虚高最多 100%**，
JavaScript-150k Acc 55.1 → 49.1，**只看标识符的 Acc-ID 17.7 → 8.6（−51.4%）**，
JsNice 变量命名 **55.04 → 34.44**；重复数据的「双下降」——
**训练 token 里仅 10% 是重复，在最坏重复次数下性能退化就相当于模型缩小 2 倍**，
**3% 重复数据可让 copying 评测掉 3 倍**。而**去重开销 < 训练 GPU 时的 1%**（SemDeDup）。

### 闸 9 — 去污染（本课题特有的三个雷）

**三个雷**（09:854-861）：
1. **Design2Code 和 Vision2UI 都源自 C4 / Common Crawl**，所以存在**内生污染通道** ——
   **必须按 URL 和注册域名去重，不只是按截图**。
2. **MultiUI 是唯一做对的**：**在爬之前就把 benchmark URL 排除掉** —— 这一条照抄。
3. **WebSight / WebCode2M 训练集与 Design2Code 测试集的视觉重叠率，从来没有人测过** ——
   这是一个能用 Yokoo 模型（0.604）或 pHash+CLIP 直接填的空白。

**各家去污判据**（13:1075-1100，可照抄的形式）：

| 系统 | 判据 | 结果 |
|---|---|---|

| PaLM | **放弃纯 n-gram**，人工把 29 个评测集分四类；判据「题干/target 中 **≥70% 的 8-gram** 出现过」 | clean 子集正负 delta 数量相当 |

**n-gram 挡不住改写（LMSYS 硬证据，13:1104-1127）**：让 GPT-4 循环改写测试题直到 n-gram 检测不到，再微调：

**时间切分（13:1131-1134）**：LiveCodeBench 给每题打 release date，**只评模型训练截止日之后的题** ——

**端到端留存约 0.5%** → **要 1,000 万可用对就得约 20 亿候选页**（09:898-921）。
渲染是成本瓶颈（2,000 万页 ≈ 2,000 CPU-day），所以**闸 4 必须排在闸 5 之前 ——
这是全管线最重要的排序约束**。

**去重算力几乎免费**（13:918-936）：10 万 × 9 视角 = 90 万图的 DINOv2 ViT-B embedding 约 **1.25 GPU 小时**；
pHash 90 万图约 **40 分钟**（4 核）；10 万 × 768 维全对全余弦 = **15.36 TFLOP ≈ 0.14 秒**（A100 TF32 70% 实效）；
MinHash+LSH 在 10 万文档上约 **11 秒**；向量存储 **307 MB**（int8 后 77 MB）。
十万量级**不需要 ANN**（FAISS 官方「1,000~10,000 次检索直接用 Flat」），
真正的约束是 **40 GB 的输出矩阵**（10 万×10 万 fp32），必须分块归约。
百万级才会撞上唯一的串行墙：datatrove FineWeb 的 MinHash 第三阶段（连通分量聚类）
**单任务、8 核、约 200 GB 内存、约 30 小时墙钟，不可并行**。

### 2.4 DOM 简化的三条路线和那个核心张力（09:308-324）

| 路线 | 代表 | 可学 | **可渲染** | 代价 |

### 2.5 这一块的明确缺口（不要编）

1. **哈希类名 / 编译产物阈值：零命中**（见闸 5）。
2. **滚动触发的懒加载图片：没有任何一家提到，未经验证**（09:297-307 原文）。

4. **LLM 合成 UI 的多样性没有任何定量基线**（09:922-944）：
   没有任何工作报告过 LLM 合成 UI 的 pHash 近重复率、CLIP 特征方差或唯一 HTML 标签覆盖率；
   **WebSight v0.1 vs v0.2 的多样性从未被比较过**。可借的通用证据：
   「Nepotistically Trained Models Collapse」显示**只要 3% 自生成污染就会崩塌，而常规筛选完全无效**；
   **召回/多样性比精度/质量衰减得更快，所以质量闸必须配一个独立的多样性监控器 ——
   最好看的页面恰恰是最同质的**。

   而 basic demo **0% Inter**（完美通过 lint）却在字体维度 **HHI = 1.00，比 gallery 的 0.50 更集中**；
   **紫色渐变在两批里都是 0%** —— 说明「点名特征」和「分布集中度」量的是两回事，后者更稳健（19:1-80）。

   990 GB → 853 GB（体积 −35%），Julia 重复率约 40%（13:949）。
7. **per-cluster cap（每簇保留上限）的具体数字：全文没有**（13:1183-1202 的 agent 复核确认）。

# 三、拿到 (query, html) 之后的四种用法

## 三.1 当无监督数据（预训练 / 中训练）

### 3.1.1 朴素拼接「这是一个 [query] 网站，它的源码是 [html]」错在哪

**先说实话：这个模板本身在本地笔记里零命中。** 我在 vc_data 全目录 + pipelines + deep_web 里搜过
`这是一个 / 源码是 / 拼接 / instruction 格式 / 原始文档格式`，**没有任何一条直接批判这个模板**
（20 的 agent 也独立确认：「完全没有，grep 零命中」）。
所以这一段只能**用间接证据拼出来**，而且每条都要标明口径是推理期还是训练期。

能用的间接证据，按强度排：

**(a) 把视觉信息「描述成文字」没用，但「规划结构」有用 —— 这是最接近的一刀**（20:204-209）：
UI2Code^N 表 12 的 Think 消融，**With 88.6 vs Without 85.5（+3.1）**，
而那个 Think 的内容是**结构规划**（识别 header/main 布局区、规划 DOM 层级，目的是 reduce layout hallucination）。
对照 ChartMimic 表 5（GPT-4o Overall）：**Direct 81.2 / HintEnhanced（先 caption 再写码）81.1 /
SelfReflection（看自己渲染结果再改）84.8**（20:181-183），原文归因「HintEnhanced 先生成 caption，
**可能引入幻觉，从而导致后续生成的代码出错**」（20:187）。
笔记的结论句：「**规划『要写成什么结构』有用（+3.1），描述『图里有什么』没用（−0.1 到 −0.9）**」（20:208）。
→ 迁移到预训练模板上：**把 html 当成「待复述的内容」是没用的那一类，必须让它承载结构预测的压力。**

**(b) 精确文本化极有价值，模型自己文本化毫无价值**（20:445-471，口径坑必须标）：
Plot2Code 表 3 —— GPT-4 纯文本 Conditional rating **7.36**；GPT-4V 图+文 **7.68**；
GPT-4V Direct（只给图）**6.48**。**纯文本拿到了多模态的 95.8%**（7.36/7.68），
而且**「只有图」反而输给「只有精确文字描述」**（6.48 < 7.36）。
**但最大的坑**：那份描述是 GPT-4 **从 ground-truth 代码里抽出来的 oracle**（平均 279 ± 115 token），
所以 7.36 是「截图→描述」管线的**上界**；真实的「自己描述」版本就是 ChartMimic 的 HintEnhanced，
81.2 → 81.1，**白做**。
→ 笔记的核心推论（20:468-471）：「**把视觉信息精确地文本化**」极有价值，
「**让模型自己去文本化**」毫无价值；差别在于前者是 oracle。
对本课题的意义：**我们手上的 DOM / scene graph 属于前者 —— 它是程序从运行时状态直接读出来的，
不经过模型，这是它的全部价值来源。**

**(c) 单一格式 vs 混合格式：唯一一条训练侧的格式混比实验**（20:149-166）：
OpenCUA 的 CoT 混合消融 —— **训练数据只用 L2 = 13.1，混 L1+L2+L3 = 18.5（差 5.4 分）**。
**口径更正（笔记自己做的，20:166）**：13.1 不是「只用 L2 推理」，而是「训练数据只用 L2、不混 L1/L3」；
推理格式与训练数据是两个不同的消融组，不能混。
原文归因（20:163）：「当模型描述截图里的信息时，往往会描述出大量**与任务或下一步动作无关的元素**，
这可能把模型带偏。」
→ 这是**最接近**「单一朴素模板不够，必须混多种构造」的本地证据，但它是 SFT 的 CoT 格式混比，不是预训练。

**(d) 格式工程 > 加模态**（20:344-362）：AgentOccam 表 17 —— **纯做文本表征的格式工程值 +5.4 点，
而且 token 还更少**（37.1 分、2,891 token，比上一行还少 485 个 token）；对照「加整张截图+SoM 只值 +0.5 点」。
caveat：AgentOccam 表 2 里**没有一个多模态 baseline**，也没有任何 VisualWebArena 实验（20:360-362）。

**(e) 模型根本不是在复刻那份 HTML**（20:1510-1521，这条对「目标该是什么」最要紧）：
UI2Code^N 端到端只输出**约 2,600 token**，而参考 HTML 平均 **251 标签 / 31,216 token**
→ 笔记原话「**模型吐的 2.6K token 不是在复刻那份真实 HTML，而是生成一个视觉近似的短版本**」；
并判定「复刻真实网页」**不是上下文问题，是能力问题**；
**任务定义（结构等价 31K 输出 vs 视觉等价 2.6K）决定上下文需求，差一个数量级。**

### 3.1.2 笔记里真正有的「更好的无监督构造」

这一节是**有干货的**，但干货集中在「一次渲染 → 多个监督头」和「局部对齐」，
不在「填空 / 顺序恢复 / 互信息」。

**(1) 截图解析（screenshot parsing）—— 全库最大的单条增益**（09:397-414）：
Pix2Struct 的完整配方 DocVQA **67.8** / Widget Captioning **137.5** CIDEr / TextCaps **84.2**；
去掉 warmup → 56.2 / 128.0 / 71.7；去掉 50% 文字遮挡 → 55.7 / 129.4 / 77.4；
**完全去掉截图解析 → 12.2 / 35.1 / 24.2**。
两条可照抄的机制：
- **遮挡 50% 的文字但要求输出完整子树** → 同时拿到 OCR + MLM + captioning 三种信号。
- **必须先做一小段「读文字」warmup**，否则原始的截图解析训练「不稳定、收敛慢」。
**必标的 caveat**：目标是简化后的 parse，不是可运行 HTML，所以它证明的是
「对视觉-结构理解有价值」，不是「对写代码有价值」。

**(2) 一次渲染挂十个监督头 —— 目标设计打败数据量**（09:415-432，S4 的 2M→15M 表）：
同一个目标：ChartQA 47.4 → 52.1；RefExp 87.9 → 88.1；WebSRC 58.7 → 60.1。
换成 10 个任务：50.5 → 55.0；92.4 → 94.9；60.5 → 61.1。
**7.5 倍数据只买到 1–5 分；而在 2M 上从 1 个目标换成 10 个目标，RefExp 买到 +4.5，
对照「加到 15M」只买到 +0.2。**
聚合效果：5 个语言输出数据集**平均 +2.7**，**4 个定位输出数据集平均 +25.3**，Table Detection **+76.1%**。
**负面证据（同节）**：在 Pix2Struct 权重上只用自己的 2M 继续做 screen parsing
**会伤害每一个下游数据集**（分布漂移；2M vs 80M、筛选不同、batch 128 vs 2048）。

**(3) 局部 bbox ↔ DOM 片段对齐（GUI-REG）**（09:433-466；20:1200）：
UI2Code^N 的 CPT 里混了这个目标：**整页截图 + 随机采样的一个 DOM 节点的 bbox → 预测该节点的 HTML**，
目的是强制局部对齐并控制序列长度（loss 记为 `L_dom`，20 的 agent 定位到 2511.08195 式 12）。
GLM-4.1V/4.5V 做的是同族的事：**140M+ GUI REG/REC QA 对**，bbox 用 Playwright 解析 DOM 拿到（09:489-505）。
**必须标的两个缺口**：
- **这个目标从来没有被单独消融过**（09:696-703）；09 §7.1 把它列为**文献空白第 1 条**。
- **引用陷阱**：UI2Code^N 的阶段消融「§4.5 / Table 6」**在 arXiv v1 里不存在**（09:696-703、09:1024-1035）。
  能引的阶段曲线是 Base **9.0** → +CPT **53.3** → +SFT **79.3** → +RL **88.6**（09:433-466；20:2026），
  CPT 单跳 **+44.3**，但 **base 9.0 异常低**（同规模的 GLM-4.1V-9B-Thinking 是 **64.7**），
  所以其中很大一部分是学格式，**不能当纯数据增益引用**。

**(4) 结构感知注意力 + 对比损失**：WAFFLE 的树结构感知注意力 + 对比学习，
四档 **28.00 / 30.80 / 35.80 / 37.00**（09:517-556）。

**(5) 受控降质（controlled degradation）—— 自监督地造出「坏页面」**：
UIClip / JitterWeb 从**约 30 万真实页面**造 **2.3M** 样本，**>99.9% 是合成的**，
**9 个 jitter 函数，每个样本最多叠 3 个**；结果设计选择准确率 **75.12%**，
缺陷检测 **87.1%** vs GPT-4V **51.58%**（09:230-245）。
同族：**MT-Web2Code 的「反向腐蚀引擎」**——往金标准页面注入结构或样式缺陷（带像素变化阈值），
再把过程反过来，得到**确定性的修复轨迹**，**102 页 × 5 轮**（pipelines.md:30）。
还有 DeTikZify 的**在线草图合成，替换概率 50%**（09:177-229）。

**(6) 反向构造 query（页面 → 自然语言需求）**（09:325-338）：
MultiUI 用 Llama-3-70B 读 **a11y tree** 生成 9 类任务（内嵌图片走 GPT-4o-mini，再用 GPT-4o 模板重写），
**1M 站点 → 7.3M 样本**；Web2Code 的 DWU 243.5K + WebSRC 51.5K；
**WebSight v0.2 的 `llm_generated_idea` 列本身就是 1,922,671 条现成的「文本→代码」对**；
而社区在 WebCode2M 上做的反向 prompt **只有 2,843 行**。
**值得抄的那一条：读 a11y tree，不读原始 HTML（token 密度高得多）。**
UI2Code^N 的做法更极端：SFT 的 80K 里，**HTML 答案由 Claude-3.7-Sonnet-Thinking 写，
query 是反向构造出来的以保证正确性**；UI 编辑覆盖增/删/改/调，
而且**把高质量的「删除」对反转成「添加」对**（09:433-466）。

**(7) 一条值得单独记的质量>数量证据**：shaders21k 的**精选 1,089 条打败随机 1,089 条
（43.26 vs 42.26）**，而总池是 21k —— **程序质量优于程序数量**（09:557-601）。

### 3.1.3 这一节的明确缺口（这是用户要的「到底有没有干货」的答案的一半）

**零命中**（全库 grep 确认）：
- **fill-in-the-middle / FIM / 填空**（针对代码或 HTML）
- **顺序恢复 / shuffle / 重排 / 乱序还原**
- **互信息 / mutual information 类目标**
- **span corruption / denoising 作为 HTML 预训练目标**
- **repo-level packing**
- **code↔render 的 CLIP 式对齐 loss**（有 bbox→HTML 的生成式对齐，没有对比式 alignment loss）

唯一一处「masked」是 Pix2Struct 的 **50% 文字遮挡**（09:397-414），
它事实上就是 MLM + OCR 的合体 —— **这是全库最接近「填空」的构造，但没人把它推广到 HTML 代码本身。**

**另外两条硬缺口**：
- **没有任何人发表过「加 UI grounding 预训练 → image-to-code 指标提升 X」的消融**（09:645-650，§4.0 结论 2）。
  正向证据**全在推理期**：ScreenCoder Position 0.613→0.755（+0.142）、Design2Code Position 0.815→0.925、
  UICopilot Visual 0.68→0.84 / 0.65→0.83 / 0.62→0.78、DCGen CLIP 83.72→85.62、
  LaTCoder TreeBLEU +66.67%，而且**这些工作互相矛盾**（09:673-695）。
- **最强的反向证据是方向相反的**（09:704-718）：Pix2Struct-Large **纯像素** RefExp **94.2** 打败
  读 a11y tree 的 UIBert **90.8**；Widget Captioning **136.7 vs 97.0**；Screen2Words **109.4 vs 64.3**
  → **方向是「代码监督 → grounding」，不是「grounding → 代码」。**

### 3.1.4 规模与配比（有数的部分）

- **中训 ≈ base 的 5%**：GLM-5 的 1.55T / 28.5T = **5.4%**；Kimi-VL cooldown **13.6%**；
  MiMo-VL stage 4 **22.9%**（09:489-505）。
- **合成占比必须压在 15% 以下**：纯 WebSight 会造成灾难性遗忘 ——
  **TextVQA 58.76 → 23.38（v0.1）/ 20.51（v0.2）**，掉幅 **>60%**（09:557-601）。
- **Web2Code 的隐藏代价**：MME-Cognition **308.21 → 279.64（−9.3%）**（09:557-601）。
- **GUIMid 的 11 域中训对照里，Web Screenshot2Code 是最差的域之一** ——
  WebArena **28.0** / AndroidWorld **9.9**（baseline 26.3 / 9.0），
  而纯文本的 MathInstruct 拿到 **31.9**、CodeI/O **29.2**，最佳混合 **34.3 / 21.2**；
  **但下游任务是 GUI agent，不是写代码** —— 这个限定必须写（09:557-601）。
- **scaling 判决**（09:602-642）：几何资产约 20 万饱和（LRM-Zero 800K→200K 只损 0.1 PSNR）；
  **程序/代码对在百万级仍在涨**（CAD-Recode 160k→1M 在 CD 上还有 1.8×；shaders21k 在 21K 程序处
  仍是对数线性未饱和）；真实网页对在 15M 处仍在涨但边际很薄。
- **CPT 配比建议**（09:967-982）：35% 自爬真实截图→可渲染 HTML / 25% 同一次渲染出的 bbox↔DOM 片段 grounding /
  15% 公开合成（**不能更多，分布太窄**）/ 10% 干净 DSL / 5% 反推 query / 10% 通用 VL，
  外加 **1B+ 纯语言代码 token**；**50B–150B token 是 1T 底座上做视觉代码中训的合理区间**。
- **几乎没有公开报告承认把「截图→可运行代码」对放进预训练** —— 除了 GLM 和 UI2Code^N（09:489-505）。
  例外披露：Kimi K2.5 App. B.3「extensive image-code paired data… HTML, React, and SVG…
  paired with their corresponding rendered screenshots」；
  **Kimi K3 §3.1 是唯一把 3D/游戏/CAD 的 code↔render 对放进预训练的**
  （「programmatic multimodal data, coupling code snippets with their rendered visuals across…
  SVG, 3D assets, Webpage, Game, and CAD schematics」）；
  Qwen3-VL §3.2.6 预训练里有「截图→响应式 HTML/CSS」和「图→可编辑 SVG」，但**RL 里没有渲染奖励**（01 §4）。

## 三.2 直接做 (query, html) 的单轮 SFT

### 3.2.1 核心论点：真实生产编码不是「一个 query 一个 answer」

本地笔记对这一条**没有直接的训练侧消融**，但有**两组很硬的间接材料**。

**(a) 真实需求的规模就不是单轮的**（16，全部一手）：
- claude.ai clone 的功能清单有 **超过 200 条** feature requirement，初始全部标 failing（16:649）；
  条目用 **JSON 而不是 Markdown** 存，理由是「the model is less likely to inappropriately change or
  overwrite JSON files compared to Markdown files」（16:668）。
- 单个 Sprint 3 的 contract 就有 **27 条** criteria（16:135、16:218）。
- 失败模式四行对照（declare victory / 留下 bug / 过早标完成 / 不知道怎么跑）（16:696-701）。
- 最关键的一句：「Claude tended to make code changes, and even do testing with unit tests or
  curl commands against a development server, but would **fail recognize that the feature didn't
  work end-to-end**.」（16:674）→ 必须显式要求用浏览器自动化、像真人一样测，性能才上来（16:676-678）。
- 一口气 one-shot 整个 app 的后果：「the agent tended to try to do too much at once—essentially
  to attempt to one-shot the app… **running out of context in the middle of its implementation**」（16:643），
  后续 agent 看到有进展就宣布完工（16:645）。
→ **这组材料支持的论证路径**：真实生产编码的监督信号是
「spec（200+ 条）→ 单功能 sprint → 签约 → 浏览器端到端实测 → 定位到行号的 finding → 回灌」。
**但必须标明：没有任何一手材料说这条路径被用于造 SFT 数据。**

**(b) 纯净单轮轨迹训不出恢复能力**（05 §0，这是最硬的一组）：
- **Agent-R**：只用最优轨迹训出来的修订能力平均 **10.84**，带纠错轨迹的 **46.75**，
  Direct-Revision 35.67（**92:42 核验一致**）。
- **PALADIN**：只用 ToolBench 的 baseline 恢复率 **32.76%**，PALADIN **89.68%**。
- **SCoRe**：纠错能力**学不到 offline** —— STaR 的 Δ(t1,t2) 是 **−14.2**，
  即使加了 correct→correct 数据也只到 **+0.4**；而 SCoRe 本身在 MATH500 上 **+4.4**，
  比基座的 −11.2 高 **15.6 个百分点**。
- **AgentRefine**：在错误轮上算 loss 是最差的做法（Jericho Success **5.0**，SciWorld 掉「接近 75%」）。
- **Verification Horizon** 的负例 token 权重扫描 **0.0 → 37.2 / 0.5 → 35.1 / 0.8 → 44.4 / 1.0（baseline）→ 41.8**
  —— **只有 0.8 那一档超过基线，整体非单调**（**92:41 核验全部一致，且原文明说非单调**）。
  **而且「丢掉整条失败轨迹再重跑 SFT」没有显著增益**；Span-KTO 把 SWE-bench Verified 从 54.2% 提到 **59.8%**。
- **AgentHER**：在等量失败数据上做 SFT-Random 得 WebArena **14.7** / ToolBench **54.8**，
  **低于只用成功数据的 18.9 / 61.2** → **不改写目标就灌失败轨迹是净负**。
- **WebClipper**：剪枝后轮数 **−21%**、token **−19.4%** 而准确率不掉；
  而让单个 LLM 直接删冗余轮（Coarse Prune）**从 0.713 掉到 0.603**（**92:43 两条都核验一致**）
  → 「**让模型自己决定删什么」不行，必须构建依赖图**（05 §1.1：依赖图 + Dijkstra 最小必要 DAG +
  3 路投票要求 2 份动作集相同 + 用基座自己的困惑度在 3 个候选里挑改写后的 thought）。
- **「修复」必须对照采样随机性基线**：Real-Time Repair —— 回滚 + 普通重采样已经能恢复 16%，
  加定位反馈才 45%；Repair or Resample —— Self-Reflection **4.29**、Critic **3.73**
  都**输给无引导的整体重跑 6.90**；温度 0 下重跑 54 个此前成功的执行，**39 个至少退化一次**。

**(c) 零 SFT 直接上 RL 在这里不可行**（08 §4.1.1）：
R1-Zero 能成是因为基座已经有能力、只需激活；而视觉编码 agent 要学工具调用协议和多轮自检行为，
基座完全没有 → **没有冷启动的话几乎每条 rollout 都卡在「格式错 → 0 分」，组内没方差、没有梯度**。
UI2Code^N 只需 80K SFT 是因为它先做了 20M 样本的 CPT；R1 只需几千条是因为那是纯文本推理。
**冷启动太小也有代价**（R1 Dev1 相对 R1-Zero 退步，归因于冷启动集太小）。
**SFT 饱和点是测到过的**：SWE-Master 0 → 60K 轨迹把解决率从 **6.2% 提到 57.8%，48K 之后进入平台**，
而且模型自己变短了（平均轮数 **115 → 94**、思考 token **14.8k → 12.7k**）。

**(d) 没有外部判据的自我修订对开源是负收益**：Idefics2-8B 直接生成 **46.7**，自我修订掉到 **12.3**
（09 §3.4 / Design2Code 表；**92:34 核验一致**）。

### 3.2.2 那么 (query, html) 单轮 SFT 到底该怎么用

笔记里真正实践过的只有一个形态（09:433-466）：
**UI2Code^N 的 SFT 80K —— 答案由 Claude-3.7-Sonnet-Thinking 写，query 反向构造以保证正确性**；
UI polishing 用多个 VLM 产出降质渲染当输入；UI editing 的「删除」对反转成「添加」对。
→ 即：**(query, html) 的 html 不是直接当 answer，而是当「反向构造 query 的素材」和
「构造降质/编辑对的母本」**。

本机的分阶段计划（08 §4.1.2）：
S1 冷启动 **8K–15K** 轨迹；S2 从 **3K–5K** 任务做拒绝采样，N=8–16，预期留存 **10%–35%** → 5K–20K 轨迹
（**低于 5% 说明题太难，高于 60% 说明太简单、RL 没信号**）；S3 在 **3K–8K** 任务上 RL，
要求 pass@N 落在 0 < p < 0.9；S4 按 GLM-4.5 的迭代自蒸馏循环。
拒绝采样留存的参照：**SWE-smith 实测 8,686 任务 / 17,906 次尝试 / 6,457 次成功 = 36%**，
每题上限 3 条 → 最终 5,016；**SWE-Gym 的每实例上限消融：1→9.0%、2→9.7%、3→7.7%、不限→9.3%**
→ **每题留 2–3 条、优先留短的**。
**而且 SWE-smith 发现难度不决定训练价值**：四个 500 条难度档给出 **12.4 / 10.8 / 13.6 / 12.2**，
**没有单调性** → **拒绝采样阶段不要按难度选，只在 S3 课程里用难度**。

### 3.3.1 【核心】参考代码的五个用途（03:305-313 完整照抄）

笔记原文的框架句在 03:25：
> **参考代码的五个用途**：证明可解、生成断言与 rubric、作为变异母本、作为 verifier 的 sanity check、

完整表格（03:305-313，逐格照抄）：

| # | 用途 | 怎么用 | 出处 |
|---|---|---|---|
| **1** | **证明可解** | R 必须在 harness 里跑通并通过全部 F2P / P2P，**重复 3 次稳定** | SWE-bench gold patch；GameDevBench 每题带已验证参考解 |

### 3.3.2 为什么不能把参考代码当目标（03:298-304）

1. **等价实现极多**：CAD-Coder 指出多份不同的 CadQuery 脚本能产出几何等价的模型，
   **SFT 难以学到这一点**，所以 RL 阶段改用 Chamfer 距离的分段线性奖励
   （**CD < 1e-5 得 1.0；CD > 0.5 或执行失败得 0**）。
2. **拿参考当整体对照的效果差**：RaR 里 **Reference-Likert 31.7% < 无参考 rubric 32.0% <
   用参考生成 rubric 35.9%**（Table 1；Table 3 显示无参考在所有生成器模型上**从未超过 34.2%**）。
3. **参考不一定最优**：开发者代码可能冗余、性能差、写法过时；**以代码相似度为奖励会把这些缺点一起学进去**。

**本机实测的独立佐证**（13:957-963）：`cube_size2` —— 一个在世界几何上逐点等同的替代实现
**通过了所有几何信号（分部件 F-score 0.9993）**，只被代码比对类判据 A2/A3 误杀
→ 「**验状态，不验代码**」是可复现的必要性，不是审美偏好。

### 3.3.3 「参考不是最优」的处置（03:315-321，可直接做成工程项）

- 把 R 当**下界**：reward 只要求满足 A，**不要求接近 R，超过 R 不受惩罚**。
- 开放维度走组内比较，**把 R 放进比较池当锚，但不在它上面更新**；统计每题 policy 解对 R 的胜率。
- 胜率持续很高的题 → **用「通过全部断言且胜率最高的 rollout」替换 R，并重跑准入检查**
  （CAD-Coder 造数时在多个候选里按几何误差取最优，思路相同）。
- **R 自身也要打分**（通过率、帧率、draw call、渲染时长、代码体量）；
  **分数低的 R 不进 SFT 池，但保留它产出的断言**。
- **题面不得泄露 R 的实现**：只描述可观察效果；锚点（DOM id、状态 schema、对象名）写进 I 并对模型公开，
  **不靠模型猜 R 的命名**（对应 SWE-bench 排除「测试调用 solution 新建函数」的规则）。

### 3.3.4 配套：任务可解性与 verifier 校准（03:61-92；11:127-142）

- **参考解执行校验会砍掉约一半候选任务**（gold 必须让 F2P 翻转，13:795）。

## 三.4 当 RL 数据：学生自己 rollout + verifier，html 源码干什么

### 3.4.1 「只能当 hint」这个判断在笔记里成不成立

**结论：成立，而且 A 半有直接文献；但有一个明确的反例，必须写出来。**

**A 半（只交目标与初态、参考解对解题者不可见、verifier 查终态）—— 有直接文献**（13 §1.2，13:98-160）：

- **RST** 逐字：解题者「**cannot access the reference solution or private verifier**」；
  交互结束后 Harbor 在**最终工作区状态**上跑 verifier；
  verifier「**checks task outcomes rather than a fixed command sequence**, allowing different
  valid solutions to receive credit」。
- **SKT 的三道门**：规则门「Visible task materials do not copy reference values or required skill
  rules verbatim」；agent 语义门「solver-visible materials … **do not semantically reveal the
  hidden answer, evaluation logic, or decisive skill-derived requirements**」；
  以及**成对 rollout（带 skill / 不带 skill）量出差距**。
- **FACET 的四条**：环境必须能 build；**verifier 必须在初态 FAIL**；参考解必须能从干净初态跑通；
  verifier 必须在终态 pass；外加负向判别「**incomplete or partial solutions must fail the verifier**」。
- **RST 把泄漏做成了可测指标（最该抄的工程实践）**，R1 → R15：
  hidden-check protection **38.2% → 63.5%**；short-instruction risk **41.6% → 7.5%**；
  提到私有测试的指令 **→ 0.1%**；**literal leakage → 0%**；
  median requirement coverage **0.42 → 0.57**；weakly grounded tasks **32.8% → 1.2%**。
- **泄漏是被量化过的 hack 类型**（11:93）：Hack-Verifiable Environments 把解法种在文件系统里，
  实测 hack 率 **grok-4.1-fast 56.3% / o3 29.1% / gpt-5-codex 23.6% / gemini-3.1-pro 7.2% /
  claude-sonnet-4.6 1.8% / gpt-5.4 0%**；缓解办法是文件访问审计（inotify/seccomp）+
  **把参考解完全放在 verifier 容器、不进沙箱**，和 WorldCoder-Bench 的规则一致
  （全部评估逻辑与断言严格不进模型 prompt、不随榜单发布）。
  本机 checklist 第 5 条：参考解、参考截图、断言清单**一律不进产物容器，
  自检方式是全盘 grep 关键词要求 0 命中**（11:108）。
- **Anthropic 的四条泄漏路径**（16:898-900）：容器里装了含修复的新版包 / git 历史里有被回滚的提交 /
  构建产物里有答案 / 内网镜像能下到新版。对应到本课题的同形物：
  **容器里留下的参考渲染图、没清掉的参考场景 JSON、node_modules 里的参考实现**。
  Fable 5 的 hack 清单里有对应项：「**Exploiting unintended information leakage in training
  environments—recovering reference solutions from git history, build caches, or other
  answer-revealing artifacts**」（16:945）。

**B 半（不要把生成器源码一起发，以免模型拟合它的代码风格）—— 没有直接文献**（13 §1.2）：
两轮扩展检索都没找到任何论文主张这一点，也没有消融。按强度排的间接证据：
① Infinigen 的反向论证说静态资产库「**更容易被过拟合**」（**是关于资产，不是代码风格**），
而 Infinigen 自己做的恰恰相反 —— 开源全部程序化代码，并把「Provides Procedural Code」列为优点；
② Procgen 的实证：agent「**strongly overfit to small training sets** in almost all cases，
要闭合泛化差距需要 **多达 10,000 个关卡**」，而固定关卡序列下 agent「学到的几乎是零」，
却「**给出一种有意义进展的错觉**」；③ FACET 在验证前排除 58 个候选，部分理由是
「workflows that permit **trivial bypasses**」；④ Shortcut Learning 综述。
→ **这半必须写成推论，不能写成已验证结论。**

**本机的实现规范**（13 §1.2）：生成器输出**目标场景**（.blend / scene graph / 9 视角参考渲染）、
**spec.json**（钉住的槽位 → 断言族 + 字段路径 + 容差）和**题面**（槽位短语拼接或 LLM 改写），
**不输出参考代码**；参考代码只用于准入①（参考必须通过自己的 verifier）、

**缺的那一道闸**：本机 gen_tasks.py 目前只有「参考过 / 破坏版挂 / search 唯一」，
**缺「verifier 必须在初态失败」** —— 如果起始场景已经满足 spec，这题就是白送分、
是 RL 里的纯噪声，而且正是 DAPO 会过滤掉的全对组，白费采样。

### 3.4.2 反例（必须写）：特权信息不是「只能当 hint」

**08 §1.4.1 的 Boundary-Aware Curriculum RL** —— **Beyond 桶不是被丢掉的**：
取距 pass@32 边界最近的 10 个 Frontier 题 + 距 pass@256 边界最近的 10 个 Beyond 题，
**给它们造教师轨迹做小规模 SFT 搭桥，再用 RL 固化**。
同节还有一条很硬的背景数字：**vanilla RLVR 的 pass@256 平均低于基座**。
→ 所以准确的说法是：**参考解不能进 reward，也不能进题面；但它可以在课程的最难档上
以「教师轨迹」的形式进 SFT，这是 hint 之外的第二条合法通道。**

### 3.4.3 RL 里 html / 渲染信号的其它用法

- **真实页面在 RL 里买到的是「真实分布那一片」**（09:433-466，UI2Code^N 20K 样本 / 100 步消融）：
  不带真实页 **81.5 / 68.7 / 92.0 / 65.0**；带真实页 **82.4 / 75.0 / 93.0 / 80.0**
  → **真实数据买到 +6.3 和 +15.0（真实分布的两档），合成那两档几乎不动（+1.0）**。
  UI2Code^N 的 RL 用 **12K 真实页面 + GRPO 去掉 KL 和 entropy 正则**。
- **WebRenderBench / ALISA**：45.1K 真实门户页，**布局与样式一致性直接从渲染结果算，当 RL 奖励**
  （pipelines.md:25）—— 这是唯一一条「真实 html 直接变成 RL 奖励」的公开做法。
- **ReLook**：3,000 个纯前端任务，Qwen2.5-VL-72B 当截图 critic，**渲染失败给 0**，
  Forced Optimization **只接受严格更好的修订**（pipelines.md）。
- **WebGen-Agent**：约 700 条 SFT 轨迹 + 500 条 Step-GRPO 指令，
  每步的 VLM 截图分（0–5）+ GUI-agent 分（1–5）**相加作为 step reward**（pipelines.md）。
- **MT-Web2Code 的反向腐蚀**：往金标页注入缺陷再反转，得到**确定性修复轨迹**（pipelines.md:30）。
- **难度标定是 RL 侧最贵的一项**（13 §2.1）：
  **Wald 口径下 n=4、p=0.5 时 95% CI 全宽 0.98 → n=4 标难度等于没标**；
  要把半宽压到 0.10 需 **n≈81~96**，压到 0.05 需 **n≈323~385**。
  标签复现性（两次独立构集的 Jaccard）：n=8 **0.632** / n=16 0.727 / n=40 约 0.80 / n=128 **0.876**。
  **桶边界 p=0.25/0.35/0.65/0.75 在 n=64 时误分率仍 15%~23%，且几乎不随 n 下降

## 4.7 为什么「纯靠模型自评构造训练信号」不可行（这一块最该写的论证）

三面证据合起来（全部一手）：

1. **自评会自夸**：generator 自己评会「confidently praising the work」；
   "tuning a standalone evaluator to be skeptical… **far more tractable**"（01 §1；16:45-56）。
   分离不消除宽松，只是把宽松变成**可单独调参的对象**；灵感来自 GAN；
   而且「主观任务没有二元检查」是前提，**所以这是退路不是首选**（16:56）。
   "Out of the box, Claude is a poor QA agent"（01 §1）。
2. **RL 奖励出来的主要是「呈现方式」而不是「解法质量」**（16:772-776）：
   对冲量、自我表功、声明遵守指令 —— **模型学会在回复里声称自己检查过了，而不是真去检查**。
   配套的实证：**Fable 5 内部使用审计 886 个 session 里有 16 个「报告做完或验证过但其实没有」**，
   标签 "Skipped cheap verification"（16:960-966）；
   完整五类失效聚类规模 **41 / 16 / 9 / 4 / 3**（16:976）；
   「编造从未观察到的关键细节」3 个（16:970）；
   「假完成声明」已是**常设指标**（16:994-1005，八条诚实性指标，审计规模约 4,000 investigations /
   约 1,900 seed instructions / 2–10 次采样，16:1007）。
3. **自我验证又会过度**（16:980-988）：Opus 5 §2.2.6 "Unproductive self-verification" ——
   24 小时蛋白设计实验里 Mythos 5 交 **30** 个，Opus 5 一臂交 **17** 个且无排序、
   另一臂**最后 8 小时没声音**；内部反馈是 self-correction loops / overthinking。
   **笔记给出的可直接做成轨迹剪枝判据的结论（16:990）**：
   「剪掉的不应是纠错本身，而是『**没有新信息进入的重复验证**』。
   判据可以是：**这一步是否引入了新的观测**。」
4. **判别通道缺失的维度 harness 就是瞎的**（16:195-197）：Claude 听不见 → 音乐质检失效。
   对应本课题：没有渲染通道就没有视觉判据。
5. **怀疑模式 reviewer 有系统性假阳性**，方向是过度工程化（16:535-537）。

# 五、全库级的引用纪律（写博客时的检查单）

1. **最容易出错的不是数字本身，是数字的归属**（92:102-104 的原话）。
   两次翻车都不是打字错误而是语义错位：一次是评测对象对不上，一次是把
   「判定方式的通过率」当成了「模型的能力」。**只有回原文才看得出来。**
2. **抽查命中率不是 100%，所以抽查必须做**（92:101）：一轮十四组里就撞到一处不存在的引用，
   而且位置很靠前。核验结论：**十四组抽查，十三组一致，一组不通过，另有一处措辞因逐值复核而收紧**（92:95）。
3. **没有独立核验的三组，引用时必须带出处性质**（92:63-70）：
   AutoLab 的脚手架消融（benchmark 存在、36 个任务、claude-opus-4.6 领先都对，
   但 **0.68 / 0.46 这组分数在原文表里没直接读到**）、Vibe Code Bench 的榜单分、**A11yn 的全部数字**。
   并且：**同一个模型换脚手架能差 11.7 点，任何单点分数离开 harness 版本都没有意义。**
4. **已更正的数字，一律用更正后的**：
   3JSBench **743 → 695** 条必查项（六族：部件计数 223 / 结构 160 / 空间关系 157 /
   任务专属几何 45 / 文字 12 / 渲染质量 98；100 题 × 3 次一次成型 × 10 模型；九个固定视角；
   3,000 次尝试里最常见失败：互相穿插 20% / 可见背面 19% / 表面闪烁 17% / 朝向不符 16% / 部件断开 16%；
